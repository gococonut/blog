## Redis再次开源

**作者:** [antirez](https://news.ycombinator.com/user?id=antirez) | **发布时间:** 2025-05-01 11:56:35

### 内容摘要

Redis 重新拥抱开源的转变

这篇帖子由 Redis 的一位核心贡献者撰写，宣布 Redis 项目已经重新回到了开源怀抱，选择了 AGPLv3 作为新的许可证。作者分享了自己过去五个月重新加入 Redis 后，积极推动从 SSPL 转向 AGPL 的历程和心路。他指出，SSPL 许可证在社区中并未得到广泛认可，OSI 和软件社区都不将其视为真正的开源许可证，这促使了内部关于许可证变更的讨论持续进行。

作者坦诚，他个人非常希望自己为新的 Vector Sets 数据类型编写的代码能够以开源许可证发布，因为编写开源软件是他长期以来的坚持和热情所在。他认为，尽管核心工作是持续改进 Redis 这个系统，但回归开源许可证是确保这些努力与 Redis 项目的初衷保持一致、赢得用户信任并融入更广泛人类集体贡献的基础。他为此感到高兴，并希望自己在这个转变中做出了一点贡献。

帖子最后提到，Redis 8 作为采用新许可证的第一个正式版本也已发布，带来了许多新特性和核心性能提升。作者表示，他将继续投入工作，通过编写高质量代码和听取用户反馈来改进 Vector Sets，并鼓励社区提出更多建议。

总的来说，这篇帖子传达了 Redis 项目重新拥抱开源，回归社区，并在 AGPLv3 许可证下继续发展和创新的重要信息，同时也表达了核心贡献者对此转变的积极态度和对未来的展望。

### 讨论焦点

讨论焦点主要围绕：1. Redis公司从BSD切换到SSPL再回到AGPL许可的行为对社区信任的影响及其合法性与道义性争议。贡献者认为被背叛，公司有权更改许可，但道义上存在问题。2. 开源项目如何可持续盈利，特别是面对超大规模云服务商（如AWS、GCP、微软）利用其免费版本赚取巨额利润而不回馈项目的困境。有人提出AGPL或更激进的“公平源代码”许可作为解决方案，但其对企业使用的影响存在争议。3. Redis的替代方案（如Valkey、Redict、Microsoft Garnet）的现状、发展以及社区转向这些替代方案的意愿和实际行动。Valkey被认为是Redis的直接竞争对手，拥有来自Fork后的改进和新增功能，并得到了部分大型企业和发行版的支持。讨论涉及Valkey的技术优势（如多线程）、社区活跃度以及企业迁移的成本和复杂性。4. 关于AGPL许可是否会“感染”企业闭源代码的法律和实际影响。有观点认为AGPL许可限制严格，企业会避免使用，也有观点认为普通使用AGPL服务器并不会影响客户端代码的许可。

## Claude 集成

**作者:** [bryanh](https://news.ycombinator.com/user?id=bryanh) | **发布时间:** 2025-05-01 12:02:14

### 内容摘要

Claude 现已支持集成，连接你的世界

Anthropic 公司于 2025 年 5 月 1 日宣布推出“集成”（Integrations）功能，这将允许其人工智能模型 Claude 与用户的应用程序和工具进行连接。这一新功能基于去年 11 月发布的“模型上下文协议”（Model Context Protocol, MCP），该协议最初仅限于通过本地服务器在 Claude 桌面版上使用，而现在“集成”功能使 Claude 能够与网络和桌面应用上的远程 MCP 服务器无缝协作。开发者可以构建和托管增强 Claude 功能的服务器，用户可以连接这些服务器。

通过连接工具，用户的工作环境信息（如项目历史、任务状态、组织知识）可以被 Claude 深入理解，使 Claude 成为更能知情的协作者，帮助用户在一个地方完成复杂的项目。目前，已经有 10 个流行服务的集成可供选择，包括 Atlassian 的 Jira 和 Confluence、Zapier、Cloudflare、Intercom、Asana、Square、Sentry、PayPal、Linear 和 Plaid，未来还将支持更多服务。开发者只需约 30 分钟即可利用提供的文档或解决方案（如 Cloudflare）构建自己的集成。

每个集成都能显著扩展 Claude 的能力。例如，通过 Zapier 集成，Claude 可以通过对话访问数千个应用程序和预建工作流程，实现自动化，甚至可以通过对话自动拉取销售数据或根据日历准备会议简报。与 Atlassian 的 Jira 和 Confluence 集成让 Claude 能够协助构建产品、管理任务，并批量处理 Confluence 页面和 Jira 工作项。

此外，Anthropic 还对 Claude 的“研究”（Research）功能进行了更新，推出了高级模式。该模式现在可以搜索网络、用户的 Google Workspace 以及通过集成连接的应用程序。Claude 可以在最多 45 分钟内进行深入调查，分解复杂请求，然后生成带有引用的全面报告。标准的报告通常在 5-15 分钟内完成，而复杂调查可能需要最多 45 分钟，这比手动研究要快得多。网络搜索功能目前已向所有付费计划的 Claude 用户全球开放。

“集成”和高级“研究”功能目前在 Max、Team 和 Enterprise 计划的 Beta 版中可用，并将很快向 Pro 计划推出。更多关于集成的信息以及 MCP 服务器的开发、安全和隐私实践可以在 Anthropic 的帮助中心找到。

## 阿努比斯从 DDoS 攻击中拯救了我们的网站的那一天

**作者:** [DoctorOW](https://news.ycombinator.com/user?id=DoctorOW) | **发布时间:** 2025-05-01 18:34:15

### 内容摘要

标题：Anubis如何拯救网站免受DDoS攻击

这篇博文讲述了ScummVM项目维护者如何利用名为Anubis的工具成功抵御了一次复杂的DDoS攻击，从而保护了他们的网站。

作者在维护ScummVM服务器基础设施时，注意到MariaDB服务器负载异常升高，起初认为是访客突然增加。然而，持续的告警和网站最终宕机揭示了问题的严重性。服务器的各个组件（Apache2、PHP-FPM、MariaDB）都达到了饱和状态，无法处理新的连接。通过日志分析，他们 발견 了大量来自全球住宅网络的IP地址发起的请求，共计约35,000个不同的IP。这些请求专门针对维基上最消耗资源的动态页面，导致服务器陷入恶性循环：数据库变慢，PHP执行缓慢，PHP-FPM资源耗尽，最终Apache2 连接也占满，网站彻底瘫痪。虽然临时增加服务器资源缓解了燃眉之急，但急需长期的解决方案来分摊应用程序的负载。

解决之道在于引入Anubis。Anubis作为一个位于代理或服务器和应用程序之间的程序，能够检查并过滤传入的连接，只将“良好”的连接转发。它通过分析用户代理、连接异常，并对声称是标准浏览器的请求发出工作量证明（proof-of-work）挑战来识别和阻止机器人。只有成功完成挑战（大约需要几秒钟）的客户端才能继续访问网站，并且该证明在一周内有效。完成挑战对普通用户而言只是显示短暂的加载画面，但对于恶意或资源受限的机器人来说，解决这种挑战将消耗大量资源，使其难以持续攻击。

部署Anubis后，服务器的数据库负载立即显著下降，告警通知消失，网站运行恢复正常。尽管攻击仍在持续，但由于Anubis有效过滤掉了恶意流量，网站保持了稳定。作者认为Anubis不仅仅是AI爬虫阻拦工具，它在实际应用中被证明是一种有效的DDoS保护手段。

### 讨论焦点

讨论集中在两方面： Anubis 的品牌形象问题（是否过于卡通化，影响专业性，以及是否允许自定义）和 Anubis 对抗 DDoS 的实际效果及替代方案（限速、缓存、以及应对大量伪造 IP 的能力）。

关于 Anubis 品牌形象的讨论：作者 herpdyderp 提出 Anubis 的卡通形象不够专业，担心客户接受度。作者 ranger_danger 和 LPisGood 都提到它是开源的，暗示可以修改。但作者 unsnap_biceps 引用 GitHub 上的讨论指出，开发者计划推出白标服务，并请求不要私自修改图片。随后作者 natebc 和 samhclark 提供了 Anubis 官方文档链接，确认官方确实不建议去除 Anubis 形象，除非签订合同进行白标定制。这部分讨论从质疑形象是否可修改，演变为确认官方立场和定制方案。

关于 Anubis 对抗 DDoS 的实际效果：作者 ranger_danger 质疑 Anubis 对抗大规模、多 IP 的真实 DDoS 攻击的能力，并提出限速和缓存是更简单有效的替代方案。对此，作者 bastawhiz 和 Ocha 反驳了限速的有效性，指出大量伪造 IP（如住宅代理）可以轻松绕过限速，导致误伤真实用户。作者 PaulDavisThe1st 则分享了 fail2ban 阻止大量伪造 IP 的经历，侧面说明了应对大量异常 IP 的复杂性，但他的例子是关于 git repo 访问，与网站 DDoS 有所区别。这部分讨论的核心在于 Anubis 和限速等传统方法应对大规模多源 DDoS 的优劣比较，存在明显分歧，特别是对限速在有大量伪造 IP 情况下的有效性。

情感倾向上，对 Anubis 品牌形象的讨论相对理性客观，旨在了解定制可能性和官方政策。对 Anubis 有效性的讨论则带有一定的质疑和辩护，反映出不同参与者对 DDoS 防御策略的理解和经验差异。

Kubetail： Kubernetes 实时日志仪表盘

Kubetail 是一款专为 Kubernetes 设计的实时日志仪表盘工具，它支持通过浏览器或终端查看日志。其核心功能是将 Kubernetes 中多容器工作负载（如 Deployment、DaemonSet）的日志合并到一个统一的、按时间顺序排列的视图中，便于用户实时追踪系统运行状态。

Kubetail 的主要入口是一个 CLI 工具 `kubetail`。通过这个工具，用户可以在本地启动一个 Web 仪表盘，或者将原始日志流式传输到终端。它的一个显著特点是直接利用 Kubernetes API 获取日志，无需将日志转发到外部服务，从而保证了数据的私密性。同时，Kubetail 还会跟踪容器生命周期事件，确保日志时间线与容器的启动、停止和替换保持同步。

项目致力于提供强大且用户友好的 Kubernetes 日志平台。主要功能包括：

- 简洁易用的界面。
- 实时查看日志信息。
- 支持按工作负载、时间范围、节点属性和 Grep 进行日志过滤。
- 通过 Kubernetes API 获取日志，默认保证数据私密性。
- Web 仪表盘可安装在桌面或集群中。
- 支持在桌面版切换多个集群。

用户可以通过 Homebrew、Shell 脚本或直接下载预编译二进制文件在桌面快速安装和启动 Kubetail。对于集群部署，则提供了 Helm Chart、YAML Manifest 或 Glasskube 等多种安装方式。安装后，通过 `kubectl port-forward` 或 Ingress 等方式即可访问 Web 仪表盘。

Kubetail 项目采用 Go、TypeScript 和 Rust 等多种语言开发，仓库结构清晰，分为 CLI 工具、Cluster API、Cluster Agent 和 Dashboard UI 等模块。项目欢迎社区贡献力量，包括 UI/UX 设计、前端开发以及问题报告和功能建议。用户可以通过邮件、Discord 或 Slack 与项目团队取得联系。

**作者:** [ingve](https://news.ycombinator.com/user?id=ingve) | **发布时间:** 2025-05-01 07:15:08

加速复制大型 SQLite 数据库的技巧

文章介绍了一种更快速、更可靠地在计算机之间复制大型 SQLite 数据库的方法。作者经常需要将远程服务器上的大型 SQLite 数据库复制到本地进行分析或备份。传统的 rsync 直接复制方式对于小型数据库有效，但随着数据库增大，尤其是包含大量索引时，复制速度会变慢且容易出错，可能导致数据库文件损坏。

核心问题在于 SQLite 数据库中的索引会显著增加文件大小，虽然索引能加速查询，但在复制过程中会重复传输数据。文章提出了一种巧妙的解决方案：利用 SQLite 内置的 `.dump` 命令，将整个数据库导出为一个文本文件。这个文本文件包含重建数据库所需的 SQL 语句，但不包含索引的实际数据，而是创建索引的命令。实验表明，通过 `.dump` 导出的文本文件比原始数据库小很多，尤其是在经过 gzip 压缩后，体积可以减小10倍以上。

基于此，新的复制流程如下：首先通过 SSH 在远程服务器上将数据库导出为 gzip 压缩的文本文件；然后使用 rsync 将这个压缩文件复制到本地；接着在本地解压缩文件；最后将文本文件通过管道输入到 SQLite 命令中，重建本地数据库。完成复制后，可以清除远程和本地的中间文件。

这种导出为文本文件的方式还有一个额外的好处：它提供了一个稳定的复制源。即使远程数据库在复制过程中发生变化，复制的始终是创建文本转储那时的数据快照，从而避免了 rsync 直接复制时可能出现的数据库文件损坏问题。作者表示，这种方法显著提高了大型 SQLite 数据库复制的效率和可靠性，强烈推荐给需要处理大型 SQLite 数据库的用户。

## C++26: 标准库中更多的 constexpr

**作者:** [npalli](https://news.ycombinator.com/user?id=npalli) | **发布时间:** 2025-05-01 14:36:58

### 内容摘要

C++26 标准库中的 constexpr 扩展：提升编译时编程能力

C++26 标准将大幅扩展 `constexpr` 在标准库中的应用范围，进一步增强 C++ 的编译时计算能力。本文深入探讨了几项关键提案，这些提案将使更多标准库功能可以在编译时使用，从而提高代码的效率和确定性。

核心内容包括：

1.  **constexpr 稳定排序 (P2562R1)**：提案旨在使 `std::stable_sort` 等稳定排序算法及其 `ranges` 版本支持 `constexpr`。结合 C++23 中已有的 `constexpr` 容器，开发者现在可以在编译时对容器进行稳定的排序操作。
2.  **\<cmath\> 和 \<complex\> 的更多 constexpr 支持 (P1383R2)**：尽管 C++23 已为部分 `<cmath>` 和 `<cstdlib>` 函数增加了 `constexpr` 支持，但仅限于行为简单的函数。此提案将对行为更复杂的数学函数（如浮点运算）增加 `constexpr` 支持，同时探讨了浮点运算在不同平台可能存在的差异问题。
3.  **trivial unions (P3074R7)**：解决了在实现 `constexpr` 容器时对未初始化存储（通常通过 `union` 实现）的需求。通过修改 `union` 的特殊成员默认行为，使其在 `constexpr` 环境下更容易使用，特别是使其默认构造函数和析构函数在满足特定条件时为 trivial。
4.  **constexpr 容器和适配器 (P3372R2)**：这项重大提案的目标是使几乎所有标准库容器和适配器都支持 `constexpr`。除 `std::hive` 和无序容器（需要用户提供 `constexpr` 哈希函数）外，绝大多数容器都将在编译时可用。
5.  **专用内存算法的 constexpr 支持 (P3508R0 和 P3369R0)**：这两项提案完善了对初始化相关算法的 `constexpr` 支持。P3508R0 修正了已接受的 P2283R2，使许多 `uninitialized_` 打头的内存算法（如 `uninitialized_copy`）支持 `constexpr`，主要涉及使用 `constexpr` placement new 进行措辞更新。P3369R0 则在此基础上，进一步为之前因技术限制未能支持 `constexpr` 的 `uninitialized_default_construct` 增加了支持。

总体而言，C++26 在标准库层面为 `constexpr` 带来了显著的扩展，涵盖了排序、数学函数、底层存储以及容器等多个方面。这极大提升了 C++ 在编译时进行复杂计算和数据结构操作的能力，为开发者编写更高性能、更具确定性的代码提供了更多可能性。文章预告下一篇将讨论编译时异常的支持。
